## Clarifications

### Session 2025-12-29

- Q: Pattern Matching快速路径的置信度阈值是多少? → A: 0.75，低于此值使用LLM Fallback
- Q: 会话上下文保留策略是什么? → A: 基于轮次，默认保留最近10轮对话，支持可配置
- Q: 意图类型与上下文加载策略如何对应? → A: Tier级别递进加载(T1:Schema→T2:+业务规则→T3:+语义关系)
- Q: 意图分类失败时如何处理? → A: 交互式澄清，列出Top-3候选意图并展示各自置信度分数，请求用户选择确认
- Q: 意图类型是否支持扩展? → A: 管理员可扩展自定义意图类型及Pattern规则，支持版本控制

## Executive Summary

### Why Build Context Graph for Data Agents?

数据类Agent在执行任务时面临三大核心挑战：

1. **语义鸿沟**: Agent难以理解业务领域的专业概念、术语关系和隐含约束
2. **上下文碎片化**: 数据源元数据、业务规则、用户意图分散在不同系统中
3. **Token效率**: 大量上下文信息导致LLM调用成本高、响应慢、甚至超限

**上下文图谱**通过结构化知识表示，为Agent提供：
- 精准的语义理解能力（知道"订单"和"客户"的关系）
- 按需加载的上下文（只获取当前任务相关的知识）
- 可推理的知识网络（从已知推导未知）

### Core Value Proposition

| 挑战 | 传统方案 | 上下文图谱方案 |
|------|---------|--------------|
| 业务理解 | 硬编码规则 | 本体驱动的语义推理 |
| 上下文获取 | 全量加载 | 按需检索+智能缓存 |
| 知识更新 | 重新部署 | 动态图谱热更新 |
| 多源整合 | 手工映射 | 语义对齐自动发现 |

## User Scenarios & Testing *(mandatory)*

### User Story 0 - Intent-Aware Query Routing (Priority: P0)

作为数据Agent系统，我需要首先识别用户查询的意图类型，以便路由到正确的处理流程并加载适当的上下文。

**Why this priority**: 意图识别是所有后续处理的前提。错误的意图分类会导致加载不相关的上下文，浪费Token并降低响应质量。

**Independent Test**: 可以通过输入14种意图类型的典型查询来测试，验证系统能正确分类并提取槽位信息。

**Acceptance Scenarios**:

1. **Given** 用户输入"海螺项目的负责人是谁?", **When** Intent Router处理请求, **Then** 分类为`query_point`意图，置信度≥0.75走快速路径
2. **Given** 用户输入"分析本月营收趋势", **When** 快速路径置信度<0.75, **Then** 系统使用LLM Fallback进行意图分类
3. **Given** 用户连续对话"那上个月呢?", **When** Context Management解析代词, **Then** 继承前一轮的时间槽位并替换为"上个月"
4. **Given** 用户输入模糊查询"看看数据情况", **When** 所有候选意图置信度均<0.75, **Then** 系统展示Top-3候选意图及置信度，请求用户选择
5. **Given** 用户查询"我的订单本月有多少", **When** 系统构建OperationContext, **Then** "我的"解析为当前用户身份，"本月"解析为基于用户时区的当前月份范围

**Supported Intent Types (10种分析意图)**:

| Tier | 优先级 | 意图标识 | 说明 | 示例 |
|------|--------|---------|------|------|
| 1 | 1 | query_point | 单点数据查询 | "海螺项目的负责人是谁?" |
| 1 | 1 | query_timeseries | 时序数据查询 | "显示过去7天的日活趋势" |
| 1 | 1 | group_aggregate | 分组聚合 | "按城市统计订单数量" |
| 2 | 2 | trend_analysis | 趋势分析 | "分析本月营收趋势" |
| 2 | 2 | distribution_analysis | 分布分析 | "各地区销售额分布" |
| 2 | 2 | topn_analysis | Top-N分析 | "销售额前10的产品" |
| 2 | 2 | comparison_analysis | 对比分析 | "对比Q1和Q2营收" |
| 3 | 3 | attribution_analysis | 归因分析 | "营收下降的主要原因" |
| 3 | 3 | anomaly_detection | 异常检测 | "检测异常订单" |
| 3 | 3 | correlation_analysis | 相关性分析 | "广告投放与销售额的相关性" |

> **Note**: 功能性意图（元数据查询、数据导出、Schema查询、血缘查询）暂不纳入意图路由，后续版本扩展。

### User Story 1 - Data Analyst Query Enhancement (Priority: P1)

作为数据分析师，我希望Agent能理解我的自然语言查询并准确转换为SQL，即使我使用业务术语而非技术字段名。

**Why this priority**: 这是数据Agent最核心的使用场景，直接影响用户能否有效使用系统。没有语义理解，Agent只能处理精确匹配的查询。

**Independent Test**: 可以通过输入"查询所有VIP客户的未完成订单"来测试，验证Agent能否正确映射"VIP客户"到`customer.level='VIP'`，"未完成订单"到`order.status NOT IN ('completed', 'cancelled')`。

**Acceptance Scenarios**:

1. **Given** 用户输入包含业务术语的查询, **When** Agent处理查询请求, **Then** 系统从上下文图谱获取术语定义并生成正确SQL
2. **Given** 查询涉及多表关联, **When** Agent需要确定JOIN路径, **Then** 系统从图谱中推导实体关系并选择最优路径
3. **Given** 用户查询包含模糊条件（如"最近"、"大额"）, **When** Agent解析语义, **Then** 系统从图谱获取业务规则定义（如"最近"=30天，"大额">10000）

### User Story 2 - Context-Aware Prompt Assembly (Priority: P1)

作为Agent开发者，我希望系统能根据当前任务自动组装最相关的上下文，而不是加载全部元数据导致token溢出。

**Why this priority**: Token效率直接影响系统可用性和成本。对于大型数据集（100+表），全量加载会导致请求失败。

**Independent Test**: 可以通过请求特定表的查询来测试，验证系统只加载相关表的schema和关联信息，而非全部数据库元数据。

**Acceptance Scenarios**:

1. **Given** 数据库有100张表, **When** 用户查询只涉及3张表, **Then** 系统只加载这3张表及其直接关联表的上下文（≤2000 tokens）
2. **Given** 设置token预算为3000, **When** 检索到的上下文超过预算, **Then** 系统按相关性排序并截断，保留最重要的内容
3. **Given** 相同查询模式重复出现, **When** 系统识别到模式匹配, **Then** 从缓存直接返回上下文（响应时间<100ms）

---

### User Story 3 - Ontology-Driven Schema Mapping (Priority: P2)

作为数据工程师，我希望能定义业务本体（OWL类、属性、关系），并自动映射到物理数据源（MySQL表、列）。

**Why this priority**: 本体映射是语义理解的基础设施，但可以先用手工配置启动，后续再自动化。

**Independent Test**: 可以通过定义一个"Customer"本体类并映射到"customers"表来测试，验证查询时Agent能正确使用映射关系。

**Acceptance Scenarios**:

1. **Given** 定义了本体类"Order"及其属性, **When** 指定映射到"orders"表, **Then** 系统建立双向索引支持语义查询
2. **Given** 本体定义了"Order belongsTo Customer"关系, **When** 物理表通过外键关联, **Then** 系统自动发现并建议映射
3. **Given** 多个数据源包含相似概念, **When** 执行跨源查询, **Then** 系统通过本体层实现语义统一

---

### User Story 4 - Dynamic Context Loading Strategy (Priority: P2)

作为系统管理员，我希望能配置不同场景的上下文加载策略，平衡精确度和性能。

**Why this priority**: 不同应用场景对上下文的需求不同，需要灵活配置。

**Independent Test**: 可以通过配置"快速模式"（只加载表名）和"完整模式"（加载完整schema）来测试，验证两种模式的响应时间和准确度差异。

**Acceptance Scenarios**:

1. **Given** 配置了"快速检索"模式, **When** 用户发起简单查询, **Then** 系统只加载一级上下文（表名、主要字段）
2. **Given** 配置了"深度分析"模式, **When** 用户发起复杂查询, **Then** 系统加载多级上下文（完整schema、业务规则、样本数据）
3. **Given** 设置了分层缓存, **When** 热点数据被频繁访问, **Then** 从L1缓存返回（延迟<10ms）

---

### User Story 5 - Knowledge Graph Visualization (Priority: P3)

作为业务用户，我希望能可视化浏览上下文图谱，理解数据之间的关系。

**Why this priority**: 可视化帮助用户理解和信任系统，但不是核心功能。

**Independent Test**: 可以通过打开图谱浏览器查看"客户-订单-产品"关系图来测试。

**Acceptance Scenarios**:

1. **Given** 用户打开图谱浏览器, **When** 选择某个实体节点, **Then** 显示其属性和关联实体
2. **Given** 图谱包含1000+节点, **When** 用户搜索特定概念, **Then** 在500ms内返回匹配结果

### Edge Cases

- **意图模糊**: 当所有候选意图置信度均低于0.75时，系统进入交互式澄清模式，展示Top-3候选意图及置信度供用户选择
- **无匹配映射**: 当用户查询的业务术语在图谱中没有定义时，系统应提示可能的近似匹配并请求用户确认
- **循环引用**: 本体关系形成循环时，加载策略应有深度限制防止无限递归
- **映射冲突**: 同一物理字段被多个本体属性映射时，系统应记录冲突并按优先级选择
- **图谱不一致**: 本体定义与物理schema不匹配时（如字段已删除），系统应标记失效映射
- **超大结果集**: 当相关上下文超过最大token预算时，系统应按相关性智能截断
- **槽位冲突**: 当新一轮对话的槽位与继承槽位冲突时，以新槽位覆盖旧槽位
- **身份缺失**: 当用户身份信息不可用时，系统应使用默认权限范围并记录警告
- **时区歧义**: 当用户时区未配置时，系统应使用服务器时区并在响应中提示
- **所有权越界**: 当查询涉及用户无权访问的数据时，系统应返回权限不足提示而非空结果

## Requirements *(mandatory)*

### Functional Requirements

#### Intent Router (意图路由层)

- **FR-100**: 系统必须支持10种核心分析意图的分类（3个Tier层级：基础查询/分析任务/高级分析）
- **FR-101**: 系统必须实现双路径意图识别：Pattern Matching快速路径（关键词+正则+置信度评分）和LLM Fallback回退路径
- **FR-102**: 当Pattern Matching置信度≥0.75时使用快速路径，否则回退到LLM分类
- **FR-103**: 系统必须支持槽位提取（Slot Extraction），包括时间、实体、指标、维度等
- **FR-104**: 系统必须维护会话上下文，支持代词解析和槽位继承
- **FR-105**: 意图分类结果必须包含：intent_type、confidence、slots、context_requirements
- **FR-106**: 系统必须基于轮次保留会话上下文，默认保留最近10轮对话，轮次数量支持配置
- **FR-107**: 系统必须根据意图Tier级别递进加载上下文：Tier 1加载Schema，Tier 2追加业务规则，Tier 3追加语义关系
- **FR-109**: 当意图分类置信度均低于阈值时，系统必须进入交互式澄清模式，展示Top-3候选意图及其置信度分数，请求用户选择确认
- **FR-110**: 系统必须支持管理员扩展自定义意图类型，包括定义意图标识、Tier层级、Pattern规则和槽位模板
- **FR-111**: 自定义意图类型必须支持版本控制，包括版本号、变更历史、回滚能力

#### Operation Context (操作上下文)

- **FR-112**: 系统必须在每次请求时构建操作上下文(OperationContext)，包含身份、时间解析、所有权、关系四个维度
- **FR-113**: 系统必须支持基于身份信息的数据权限过滤，包括行级权限(RLS)和列级权限(CLS)
- **FR-114**: 系统必须支持相对时间表达式的解析，根据用户时区和配置的财年起始日期进行标准化
- **FR-115**: 系统必须支持代词"我/我的"到当前用户身份的解析，以及"我们/本部门"到组织层级的解析

#### Core Graph Capabilities

- **FR-001**: 系统必须支持创建、更新、删除本体类（OWL Class）及其层级关系
- **FR-002**: 系统必须支持定义数据属性（DataProperty）和对象属性（ObjectProperty）
- **FR-003**: 系统必须支持本体类到物理数据源（表/视图）的映射配置
- **FR-004**: 系统必须支持属性到物理字段的映射，包括类型转换规则
- **FR-005**: 系统必须维护本体元素的版本历史，支持回滚

#### Context Retrieval

- **FR-006**: 系统必须提供基于自然语言查询的上下文检索API
- **FR-007**: 系统必须支持多级上下文检索（粗筛→精筛→扩展→增强）
- **FR-008**: 系统必须根据Token预算动态调整返回的上下文详细程度
- **FR-009**: 系统必须支持基于语义相似度的相关性排序
- **FR-010**: 系统必须缓存频繁访问的上下文片段

#### Loading Strategy

- **FR-011**: 系统必须支持配置不同的加载策略模板（快速/标准/深度）
- **FR-012**: 系统必须支持按数据源、场景、用户角色配置加载策略
- **FR-013**: 系统必须实现三级缓存（会话级/数据源级/全局级）
- **FR-014**: 系统必须支持预热常用上下文到缓存

#### Integration

- **FR-015**: 系统必须与现有DB-GPT的Chat场景无缝集成
- **FR-016**: 系统必须支持从Neo4j/TuGraph加载本体定义
- **FR-017**: 系统必须支持从MySQL/PostgreSQL等数据源自动发现schema
- **FR-018**: 系统必须提供上下文图谱的导入/导出功能

### Key Entities

- **IntentClassification**: 意图分类结果。包含意图类型(10种核心分析意图+自定义扩展)、置信度分数、匹配路径(pattern/llm)、提取的槽位列表。

- **SlotValue**: 槽位值。包含槽位类型(时间/实体/指标/维度/数值)、原始文本、规范化值、是否继承自上轮对话。

- **ConversationContext**: 会话上下文。包含会话ID、历史意图序列(默认最近10轮，可配置)、当前槽位状态、代词引用栈、轮次保留配置、操作上下文引用。

- **OperationContext**: 操作上下文，封装单次请求的运行时环境信息。包含：
  - **身份(Identity)**: 当前用户ID、角色、权限范围、所属组织/部门
  - **时间解析(TimeResolution)**: 当前时间、时区、"今天/本周/本月"等相对时间的锚点、财年起始配置
  - **所有权(Ownership)**: 数据所有者、可访问的数据源列表、行级/列级权限过滤条件
  - **关系(Relationships)**: 当前用户与查询实体的关系（如"我的订单"中"我"的解析）、组织层级关系

- **IntentDefinition**: 意图定义(支持扩展)。包含意图标识、显示名称、Tier层级、Pattern规则列表、槽位模板、上下文加载配置、版本号、创建者、变更历史。

- **OntologyClass**: 本体类，表示业务领域的核心概念（如"客户"、"订单"）。包含类名、描述、父类引用、关联的数据源映射。

- **OntologyProperty**: 本体属性，包括数据属性（描述实体特征）和对象属性（描述实体关系）。包含属性名、类型、所属类、值域约束。

- **SourceMapping**: 本体到物理源的映射。包含本体元素引用、数据源标识、物理对象路径（表名/列名）、转换规则。

- **ContextFragment**: 上下文片段，可缓存和组合的知识单元。包含内容类型、文本内容、Token数量、相关性分数、有效期。

- **LoadingStrategy**: 加载策略配置。包含策略名称、触发条件、检索深度、Token预算、缓存配置。

- **ContextCache**: 缓存条目。包含缓存键、内容、层级（L1/L2/L3）、命中次数、过期时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用上下文图谱后，Agent对业务术语查询的正确理解率从基线提升至90%以上
- **SC-002**: 对于100表规模的数据库，上下文加载时间从全量加载的5秒降至按需加载的500ms以内
- **SC-003**: 单次查询的上下文Token消耗控制在设定预算的±10%范围内
- **SC-004**: 缓存命中场景下，上下文获取延迟低于100ms
- **SC-005**: 系统支持10000+本体元素的图谱规模，检索延迟保持稳定
- **SC-006**: 用户无需修改查询语句，只通过配置映射即可适配新数据源
- **SC-007**: 本体更新后，相关查询在30秒内自动使用新定义（缓存失效）

## Assumptions

基于行业最佳实践，本规格做出以下假设：

1. **本体建模采用OWL标准**: 使用W3C OWL语义Web标准作为本体表示格式
2. **图存储使用Neo4j**: 基于项目现有集成，优先使用Neo4j作为图谱存储
3. **缓存使用Redis**: 全局缓存层使用Redis实现，会话缓存使用内存
4. **Token预算默认3000**: 参考GPT-4上下文窗口，设置合理的默认Token预算
5. **相关性算法基于向量相似度**: 使用embedding向量计算语义相关性
6. **映射配置存储在关系库**: 映射元数据存储在MySQL便于管理
7. **支持中英文双语**: 本体名称和描述支持中英文，以适应国际化需求

---

## Out of Scope

以下内容不在本功能范围内：

1. 本体自动学习/发现（从数据自动生成本体）
2. 跨组织的本体联邦查询
3. 本体推理引擎（OWL DL完整推理）
4. 图谱的协同编辑和版本合并
5. 非结构化数据（文档、图片）的知识抽取
